เวลาให้ AI สร้างหน้าเว็บ โค้ดอาจรันได้ตั้งแต่ครั้งแรก แต่หน้าเว็บยังอ่านยาก ปุ่มสำคัญไม่เด่น หรือทุกส่วนดูมีน้ำหนักเท่ากัน การสั่งว่า “ทำให้สวยขึ้น” เปิดช่องให้ agent เดาว่าเราต้องการอะไร

**[Impeccable](https://impeccable.style/)** ของ pbakaus เป็น skill ที่เพิ่มแนวทางออกแบบ frontend ให้ AI coding agent ใช้ได้ทั้งสร้าง UI ใหม่และปรับงานเดิม ครอบคลุมตั้งแต่ typography และ layout ไปจนถึงข้อความ สี และการใช้งานบนหลายขนาดจอ จุดที่น่าสนใจคือเราสามารถระบุชนิดของการปรับปรุงได้ชัดขึ้นผ่านคำสั่งเฉพาะทาง ตามภาพรวมบน [skills.sh](https://www.skills.sh/pbakaus/impeccable/impeccable)

## เริ่มต้นอย่างไร

ถ้าอ่านบทความ [skills.sh](/th/knowledge/skills-sh) มาแล้ว สามารถติดตั้ง shared skill จากลิงก์นี้ได้ด้วยคำสั่ง

```bash
npx skills add https://github.com/pbakaus/impeccable --skill impeccable
```

อีกทางหนึ่ง [เอกสาร Impeccable](https://impeccable.style/docs/) แนะนำ installer ของโปรเจกต์ ซึ่งให้เลือก coding tool และขอบเขตการติดตั้ง พร้อม integration ที่เหมาะกับเครื่องมือนั้น

```bash
npx impeccable install
```

เลือกใช้วิธีใดวิธีหนึ่ง จากนั้นเริ่มในแชตของ agent ด้วย

```text
/impeccable init
```

ขั้นตอนนี้ช่วยบันทึกบริบทผู้ใช้และเป้าหมายลง `PRODUCT.md` ส่วนแนวทางภาพของโปรเจกต์อยู่ใน `DESIGN.md` ตาม [README ของโปรเจกต์](https://github.com/pbakaus/impeccable) การแยกสองส่วนนี้ช่วยให้เปลี่ยนหน้าตาโดยยังยึดเป้าหมายของผลิตภัณฑ์

## Commands ทั้งหมด: ทำอะไร ใช้เมื่อไร

[Command Reference](https://impeccable.style/docs/) ณ วันที่ 16 ตุลาคม 2026 แบ่ง 24 รายการเป็น 6 กลุ่ม ด้านล่างสรุปหน้าที่และจังหวะที่เหมาะกับแต่ละคำสั่ง พร้อมตัวอย่าง prompt ที่นำไปปรับใช้ได้ ตัวอย่างเป็นคำขอประกอบบทความ ไม่ใช่ผลการรันจริง

รูปแบบทั่วไปคือเรียก skill ตามด้วยคำสั่งและเป้าหมาย โดยพิมพ์ในแชตของ agent

```text
/impeccable <command> <target หรือคำอธิบายสิ่งที่ต้องการ>
```

บาง agent ใช้รูปแบบเรียก skill ต่างกัน ให้เลือกจากรายการ skill ของเครื่องมือที่ใช้อยู่ ส่วนตัวอย่างด้านล่างใช้รูปแบบ `/impeccable` ตามเอกสาร

### Create — สร้างงานและวางแผน

**1. [impeccable](https://impeccable.style/docs/impeccable/) — จุดเริ่มต้นเมื่อยังไม่รู้ว่าจะใช้คำสั่งไหน**

บอกสิ่งที่ต้องการสร้างหรือปรับปรุงเป็นภาษาธรรมดา แล้วให้ skill เลือกแนวทางทำงานที่เหมาะสม ใช้ได้ทั้งหน้าใหม่และงานเดิม โดยควรระบุเป้าหมายและสิ่งที่ต้องรักษาไว้ ถ้าเรียก `/impeccable` เปล่า ๆ จะเสนอขั้นตอนถัดไปให้เลือกก่อนเริ่มทำ

ตัวอย่าง: `/impeccable ออกแบบหน้าจองเวิร์กช็อป ให้เห็นวันจัด ราคา และปุ่มจองชัดเจน`

**2. [shape](https://impeccable.style/docs/shape/) — ตกผลึกโจทย์ก่อนเขียนโค้ด**

ช่วยกำหนดผู้ใช้ งานที่ต้องทำ เนื้อหา สถานะ ข้อจำกัด และทิศทาง UX/UI จบด้วย brief ที่ตกลงร่วมกันและหยุดก่อน implementation เหมาะเมื่อยังมีไอเดียคร่าว ๆ หรืออยากตรวจแผนก่อนให้ agent ลงมือสร้าง

ตัวอย่าง: `/impeccable shape หน้าตั้งค่าการแจ้งเตือน ให้ผู้ใช้ลดความถี่ได้โดยไม่ต้องปิดทั้งหมด`

### Evaluate — ประเมินปัญหาก่อนแก้

**3. [audit](https://impeccable.style/docs/audit/) — ตรวจคุณภาพ implementation**

ตรวจ accessibility, performance, theme, responsive behavior และความสม่ำเสมอของ implementation แล้วรายงานปัญหาตามความรุนแรง โดยยังไม่แก้โค้ด เหมาะก่อนปล่อยงานหรือหลังเปลี่ยนส่วนสำคัญ ควรอ่านปัญหาที่ขัดขวางผู้ใช้ก่อนดูคะแนนรวม

ตัวอย่าง: `/impeccable audit ขั้นตอนชำระเงิน ตรวจคีย์บอร์ด dark mode และการใช้งานบนมือถือ`

**4. [critique](https://impeccable.style/docs/critique/) — วิจารณ์ดีไซน์และความชัดเจนของประสบการณ์**

ประเมิน hierarchy, usability, เอกลักษณ์ และสิ่งที่ทำให้หน้าดูสับสน พร้อมชี้สิ่งที่ควรรักษาและลำดับการปรับปรุง คำสั่งนี้ให้ข้อเสนอโดยยังไม่เปลี่ยนดีไซน์ เหมาะเมื่อรู้สึกว่างานยังไม่ลงตัวแต่บอกสาเหตุไม่ถูก

ตัวอย่าง: `/impeccable critique หน้าราคา ผู้ใช้ควรเปรียบเทียบแพ็กเกจและเลือกได้ง่าย`

### Refine — ปรับรายละเอียดและบุคลิก

**5. [animate](https://impeccable.style/docs/animate/) — ใช้ motion อธิบายสิ่งที่เปลี่ยน**

เพิ่ม feedback และความต่อเนื่องให้ interaction เช่น การย้ายรายการ เปิด panel หรือบันทึกสำเร็จ เหมาะเมื่อผู้ใช้ตามการเปลี่ยนสถานะไม่ทัน ต้องคำนึงถึงการกดซ้ำ การขัดจังหวะ performance และการตั้งค่า reduced motion

ตัวอย่าง: `/impeccable animate การย้ายงานไปคอลัมน์เสร็จแล้ว ให้ตามตำแหน่งใหม่ได้ง่าย`

**6. [bolder](https://impeccable.style/docs/bolder/) — ทำส่วนสำคัญให้มีน้ำหนักขึ้น**

ปรับสัดส่วน การจัดวาง และการเน้นให้ส่วนที่จืดหรือกลืนกับหน้าเด่นขึ้น โดยใช้ภาษาภาพที่โปรเจกต์มีอยู่ เหมาะกับ section ที่ควรนำสายตา ควรระบุเป้าหมายให้ชัดเพื่อไม่ให้ทุกส่วนแข่งกันเด่น

ตัวอย่าง: `/impeccable bolder ส่วนผลงาน ให้โปรเจกต์หลักเด่นขึ้นและคงสีแบรนด์เดิม`

**7. [colorize](https://impeccable.style/docs/colorize/) — ให้สีช่วยสื่อความหมาย**

ใช้สีแยก action, selection และสถานะ หรือเสริมบรรยากาศของดีไซน์ เหมาะกับหน้าที่ดูเรียบจนแยกข้อมูลไม่ออก โดยยึด token และความหมายสีเดิม ตรวจ contrast และมีข้อความหรือสัญญาณอื่นประกอบเพื่อไม่ให้พึ่งสีอย่างเดียว

ตัวอย่าง: `/impeccable colorize หน้ารายการบทความ ให้แยกเผยแพร่แล้วกับฉบับร่างง่ายขึ้น`

**8. [delight](https://impeccable.style/docs/delight/) — เพิ่มรายละเอียดที่ทำให้ประสบการณ์น่าจดจำ**

ออกแบบการตอบสนองที่เข้ากับบุคลิกผลิตภัณฑ์ เช่น ช่วงสร้างสิ่งแรกหรือทำเป้าหมายสำเร็จ เหมาะเมื่อ flow ใช้งานได้แล้วแต่ยังขาดความรู้สึกเฉพาะตัว ควรลองซ้ำหลายครั้งเพื่อให้แน่ใจว่ารายละเอียดนั้นไม่กลายเป็นสิ่งที่ต้องนั่งรอ

ตัวอย่าง: `/impeccable delight ตอนสร้างสมุดบันทึกเล่มแรก ให้รู้สึกเป็นของตัวเองโดยไม่ขวางการพิมพ์`

**9. [layout](https://impeccable.style/docs/layout/) — จัดโครงหน้าและจังหวะพื้นที่ใหม่**

ปรับ reading order, grouping, spacing และ density ภายใต้สไตล์เดิม เหมาะเมื่อข้อมูลที่จำเป็นมีครบแต่กระจัดกระจายหรือจับคู่ label กับ control ยาก ต้องตรวจให้ลำดับที่มองเห็นสอดคล้องกับลำดับการใช้คีย์บอร์ดด้วย

ตัวอย่าง: `/impeccable layout หน้าตั้งค่าบัญชี จัดข้อมูลส่วนตัวและความปลอดภัยให้เป็นกลุ่มชัดเจน`

**10. [overdrive](https://impeccable.style/docs/overdrive/) — ผลักประสบการณ์ให้โดดเด่นทางเทคนิค**

สำรวจ interaction หรือการแสดงผลที่ทะเยอทะยาน เช่น custom rendering, shader หรือ physics โดยเสนอแนวทางและ trade-off ให้เลือกก่อนสร้าง เหมาะกับจุดที่ความพิเศษมีคุณค่าต่องาน ต้องมี fallback และตรวจต้นทุนบนอุปกรณ์เป้าหมาย

ตัวอย่าง: `/impeccable overdrive หน้าชมประติมากรรม ให้หมุนและเปลี่ยนรูปทรงได้ พร้อมทางเลือกสำหรับเครื่องที่ไม่รองรับ`

**11. [quieter](https://impeccable.style/docs/quieter/) — ลดความเข้มของสิ่งที่แย่งความสนใจ**

ลดสีเน้น น้ำหนัก เงา เส้นตกแต่ง หรือ motion ที่มากเกินไป เหมาะเมื่อเนื้อหาถูกต้องแล้วแต่หน้าอ่านเหนื่อย ต้องรักษา contrast, focus และจุดสำคัญให้เห็นได้ชัด ไม่ทำให้ทุกอย่างซีดหรือเหมือนกันหมด

ตัวอย่าง: `/impeccable quieter การ์ดแพ็กเกจ ลดของตกแต่งและทำให้เทียบราคาได้สบายตาขึ้น`

**12. [typeset](https://impeccable.style/docs/typeset/) — ปรับระบบตัวอักษรให้อ่านและสแกนง่าย**

ปรับบทบาทของหัวข้อ เนื้อหา label และข้อความรอง ผ่านขนาด น้ำหนัก ความยาวบรรทัดและระยะบรรทัด เหมาะเมื่อข้อความแต่ละระดับดูเหมือนกัน หรือบทความยาวอ่านเหนื่อย ตรวจการ zoom ข้อความยาว และจอแคบด้วย

ตัวอย่าง: `/impeccable typeset หน้าบทความภาษาไทย ใช้ฟอนต์เดิมและทำให้หัวข้อแต่ละระดับแยกกันชัด`

### Simplify — ลดภาระในการใช้งาน

**13. [adapt](https://impeccable.style/docs/adapt/) — ปรับให้เหมาะกับอุปกรณ์หรือบริบทใหม่**

ปรับ layout, navigation, ความสำคัญของข้อมูล และวิธีป้อนข้อมูล เช่น ย้าย dashboard จาก desktop มาสู่มือถือ เหมาะเมื่อการย่อขนาดอย่างเดียวไม่พอ ต้องรักษางานหลักให้ทำได้และปรับ interaction ที่เคยพึ่ง hover ให้ใช้กับ touch ได้

ตัวอย่าง: `/impeccable adapt หน้าติดตามคำสั่งซื้อสำหรับมือถือ ให้สถานะและปุ่มติดตามเข้าถึงง่าย`

**14. [clarify](https://impeccable.style/docs/clarify/) — เขียนข้อความ UI ให้รู้ว่าต้องทำอะไรต่อ**

ปรับชื่อปุ่ม label คำแนะนำ error และข้อความในสถานะต่าง ๆ ให้ตรงกับสิ่งที่ระบบทำ เหมาะเมื่อผู้ใช้ไม่เข้าใจคำศัพท์หรือเจอข้อความที่ไม่ช่วยแก้ปัญหา ต้องรักษาข้อเท็จจริงและไม่เดาสาเหตุของ error ที่ระบบยังไม่รู้

ตัวอย่าง: `/impeccable clarify ฟอร์มแก้ไขโปรไฟล์ รวมคำแนะนำการกรอกและข้อความบันทึกไม่สำเร็จ`

**15. [distill](https://impeccable.style/docs/distill/) — ลดสิ่งที่ทำให้โจทย์หลักถูกกลบ**

ตัดข้อมูลซ้ำ รวมส่วนที่เกี่ยวข้อง และค่อยแสดงตัวเลือกที่ใช้เป็นครั้งคราวเมื่อจำเป็น เหมาะเมื่อหน้าบังคับให้รับข้อมูลมากเกินไปในคราวเดียว ต้องเก็บข้อมูลสำคัญต่อการตัดสินใจและเส้นทางรองที่ผู้ใช้ยังต้องใช้

ตัวอย่าง: `/impeccable distill หน้าชำระเงิน เน้นยอดรวมและการจ่าย แต่ยังเปิดตัวเลือกข้อความของขวัญได้`

### Harden — เตรียมพร้อมกับการใช้งานจริง

**16. [harden](https://impeccable.style/docs/harden/) — รับมือข้อมูลสุดขั้วและสถานะผิดพลาด**

เพิ่มการจัดการข้อความยาว ข้อมูลว่าง network error คำแปล การกดส่งซ้ำ และกรณีที่ทำให้ UI พัง เหมาะเมื่อหน้าทำงานกับข้อมูลตัวอย่างได้แต่ยังเปราะกับสถานการณ์จริง เช่น เก็บข้อความที่กรอกไว้เมื่อบันทึกไม่สำเร็จ

ตัวอย่าง: `/impeccable harden ฟอร์มที่อยู่ รองรับชื่อยาว ป้องกันส่งซ้ำ และเก็บค่าที่กรอกเมื่อเน็ตหลุด`

**17. [onboard](https://impeccable.style/docs/onboard/) — พาไปถึงผลลัพธ์แรกที่มีคุณค่า**

ปรับ first-use flow, empty state, ตัวอย่างข้อมูลและคำแนะนำให้เริ่มใช้งานได้จริง เหมาะเมื่อคนเข้ามาแล้วไม่รู้ว่าจะเริ่มตรงไหนหรือหลุดระหว่าง setup ควรให้ข้ามคำแนะนำได้ และไม่รบกวนคนที่ทำขั้นตอนนั้นเสร็จแล้ว

ตัวอย่าง: `/impeccable onboard หน้ารายงาน ให้ลองดูข้อมูลตัวอย่างที่ติดป้ายชัดก่อนเชื่อมข้อมูลจริง`

**18. [optimize](https://impeccable.style/docs/optimize/) — แก้ความช้าจากคอขวดที่วัดได้**

ตรวจ loading, rendering, interaction, asset และ animation เพื่อหางานที่แพงหรือไม่จำเป็น แล้วเปรียบเทียบก่อน–หลังภายใต้เงื่อนไขใกล้เคียงกัน เหมาะกับหน้าที่เปิดช้า เลื่อนกระตุก หรือกดแล้วตอบสนองช้า

ตัวอย่าง: `/impeccable optimize หน้ารายงานที่เปิดช้าบนมือถือ วัดก่อนและหลังโดยคงฟังก์ชันเดิม`

**19. [polish](https://impeccable.style/docs/polish/) — เก็บงานให้สม่ำเสมอและพร้อมส่ง**

ปรับ spacing, typography, alignment, copy, interaction และสถานะที่ยังขาด โดยยึดทิศทางภาพและ design system เดิม เหมาะเมื่อดีไซน์หลักถูกทางแล้วและอยากเก็บหลายรายละเอียดร่วมกัน ปัญหาที่ขัดขวางผู้ใช้มาก่อนความสวยงามจุดเล็ก ๆ

ตัวอย่าง: `/impeccable polish หน้าชำระเงิน คง layout และสีเดิม พร้อมตรวจ loading และ error state`

### System — บันทึกระบบและทำงานผ่าน browser

**20. [document](https://impeccable.style/docs/document/) — บันทึก visual system ที่ใช้อยู่**

อ่านสี typography, layout และกฎ component จากงานจริง แล้วบันทึกใน `DESIGN.md` พร้อม metadata เพิ่มเติมใน `.impeccable/design.json` เหมาะเมื่อมีสไตล์ที่ต้องการให้งานถัดไปทำตาม ถ้ายังไม่มี implementation ใช้ `document --seed` เพื่อวางบันทึกตั้งต้น และสแกนใหม่หลังมีโค้ดจริง

ตัวอย่าง: `/impeccable document`

**21. [extract](https://impeccable.style/docs/extract/) — รวม pattern ซ้ำเป็นโค้ดที่ใช้ร่วมกัน**

ค้นหา component, token และรูปแบบที่ซ้ำด้วยเจตนาเดียวกัน แล้วสร้างส่วนกลางพร้อมย้ายจุดใช้งานเดิม เหมาะเมื่อแก้ปุ่มหรือ spacing แล้วต้องตามแก้หลายหน้า ต่างจาก `document` ตรงที่คำสั่งนี้ปรับ implementation ให้ใช้ร่วมกันจริง

ตัวอย่าง: `/impeccable extract ปุ่มหลักในหน้าสั่งซื้อ บัญชี และจัดการสินค้า โดยรักษาพฤติกรรมแต่ละหน้า`

**22. [generate](https://impeccable.style/docs/generate/) — ขอ variants ของ element จากแชต**

ระบุ element ทิศทาง และจำนวนตัวเลือก แล้วให้ agent หาเป้าหมายและเปิดเทียบในหน้าเว็บผ่าน Live Mode ขอได้ 1–8 แบบ ค่าเริ่มต้น 3 แบบ เหมาะเมื่อรู้ตำแหน่งที่อยากปรับแล้ว โดย Accept เก็บแบบที่เลือกลง source และ Discard คืนของเดิม

ตัวอย่าง: `/impeccable generate 3 quieter variants of the pricing cards`

**23. [init](https://impeccable.style/docs/init/) — เก็บบริบทผลิตภัณฑ์ให้ใช้ต่อได้**

อ่านโปรเจกต์ ถามข้อมูลที่ยังขาด และบันทึกผู้ใช้ เป้าหมาย ข้อจำกัดกับข้อเท็จจริงใน `PRODUCT.md` เหมาะตอนเริ่มใช้หรือเมื่อบริบทสำคัญเปลี่ยน คำสั่งนี้ไม่ได้เลือก palette ใหม่หรือเขียน `DESIGN.md`; ใช้ `document` เมื่อต้องการบันทึกระบบภาพ

ตัวอย่าง: `/impeccable init`

**24. [live](https://impeccable.style/docs/live/) — เลือกและปรับงานในหน้าเว็บจริง**

เปิดเครื่องมือให้เลือก element ใส่ comment หรือ annotation แล้วเปรียบเทียบและรับ variants ใน browser ต่างจาก `generate` ที่เริ่มด้วยการระบุเป้าหมายในแชต โหมดนี้ยังเป็น beta ต้องเปิด agent session ค้างไว้ และใช้กับเว็บบน development server หรือ local HTML

ตัวอย่าง: `/impeccable live`

### craft และคำสั่งลัด pin / unpin

**[craft](https://github.com/pbakaus/impeccable#24-commands)** ยังอยู่ในตารางคำสั่งของ README โดยอธิบายว่าเป็น flow วางแผนแล้วสร้าง พร้อมวนตรวจผลภาพ เช่น `/impeccable craft หน้าจองเวิร์กช็อป` ขณะที่เว็บไซต์จัดจุดเริ่มต้นงานสร้างไว้ใต้คำสั่ง `impeccable` โดยตรง หากรายการในเวอร์ชันที่ติดตั้งต่างจากบทความ ให้ตรวจรายการของ skill นั้นก่อนใช้งาน

**[pin / unpin](https://impeccable.style/docs/impeccable/)** ใช้เพิ่มหรือลบ shortcut ของคำสั่งที่เรียกบ่อย โดย shortcut ยังส่งงานเข้า skill หลัก เช่น

```text
/impeccable pin audit
/audit หน้าชำระเงิน
/impeccable unpin audit
```

## เลือกคำสั่งที่ใกล้ปัญหาที่สุด

- **ยังอธิบายปัญหาไม่ถูก** — เริ่ม `critique`; ถ้ากังวล implementation ให้ใช้ `audit`
- **มีข้อมูลครบแต่จัดไม่ดี** — ใช้ `layout`; ถ้าข้อมูลซ้ำหรือเยอะเกินไปให้ใช้ `distill`
- **อ่านยาก** — ใช้ `typeset` กับรูปแบบตัวอักษร และ `clarify` กับความหมายของข้อความ
- **น้ำหนักภาพไม่พอดี** — ใช้ `bolder` กับส่วนที่ควรนำสายตา หรือ `quieter` กับส่วนที่แย่งความสนใจ
- **อยากลองหลายแบบก่อนเลือก** — ใช้ `generate` เมื่อระบุ element ได้ หรือ `live` เมื่ออยากเลือกใน browser
- **เตรียมส่งงาน** — ใช้ `harden` กับ edge cases, `optimize` กับความช้า และ `polish` เพื่อเก็บรายละเอียด

## ตัวอย่าง workflow สำหรับหน้าสมัครสมาชิก

แนวทางที่ผมแนะนำคือเริ่มจากปัญหาที่สังเกตได้ เช่น “คนอ่านไม่รู้ว่าต้องกรอกอะไรก่อน” แทนการขอเปลี่ยนสไตล์ทั้งหน้า

1. **ให้บริบท** — ใครสมัคร สมัครเพื่ออะไร และข้อมูลใดจำเป็นจริง
2. **ขอ critique ก่อน** — ให้ agent ชี้จุดที่แย่งความสนใจหรือทำให้ตัดสินใจยาก
3. **แก้ทีละเรื่อง** — เช่น ทำ label ให้ชัด ลดข้อความซ้ำ แล้วค่อยปรับ spacing
4. **เปิดตรวจหน้าจริง** — ลองบนมือถือ ใช้คีย์บอร์ด และกรอกข้อมูลผิดเพื่อดู error state

ตัวอย่าง prompt ที่นำไปปรับใช้ได้

```text
ตรวจหน้าสมัครสมาชิกสำหรับคนที่เข้ามาครั้งแรก
เป้าหมายคือให้รู้ว่าต้องกรอกอะไรและจะเกิดอะไรหลังส่งฟอร์ม
เริ่มจากอธิบายปัญหา 3 จุดที่กระทบการใช้งานมากที่สุด
เมื่อแก้แล้ว ให้ตรวจข้อความภาษาไทยยาว ๆ และหน้าจอมือถือด้วย
```

ส่วนนี้เป็นข้อเสนอ workflow สำหรับนำไปทดลอง ไม่ใช่ผลทดสอบของ Impeccable กับเว็บไซต์นี้

## ใช้เป็นตัวช่วยตัดสินใจ แล้วตรวจผลจริง

Impeccable เหมาะกับงานที่ต้องคุยกับ agent เรื่องคุณภาพ UI ให้เฉพาะเจาะจงขึ้น โดยเฉพาะตอนมีหน้าที่ทำงานได้แล้วแต่ยังต้องเก็บรายละเอียด สำหรับผม เกณฑ์ตัดสินควรเป็นสิ่งที่ผู้ใช้ทำได้ดีขึ้น เช่น อ่านข้อมูลสำคัญเจอ กรอกฟอร์มสำเร็จ และเข้าใจสถานะของระบบ

หลังปรับงาน ควรเทียบกับเป้าหมายเดิมและเปิดดูผลลัพธ์จริงเสมอ คำแนะนำจาก skill เป็นจุดเริ่มต้นของการปรับปรุง ส่วนความเหมาะสมกับแบรนด์ เนื้อหา และผู้ใช้ยังต้องใช้วิจารณญาณของทีม
